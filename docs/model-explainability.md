# 予測理由の設計

## 目的

一般ユーザーが、予測価格を単一の正解と受け取らず、どの入力条件がモデル上の価格差へ結び付いたかを
短時間で理解できるようにする。表示する理由は因果効果ではなく、現在のモデルと比較条件に基づく
予測差分である。

## 候補比較

| 方式 | 個別入力への対応 | ブラウザ負荷 | 配信容量 | 説明しやすさ | 判断 |
| --- | --- | ---: | ---: | --- | --- |
| 学習側TreeSHAP集計 | 区分単位 | 小 | 中〜大 | SHAPの説明が必要 | 将来候補 |
| 条件変更差分 | 個別入力 | 推論4〜5回 | 追加なし | 「基準条件との差」と説明できる | MVP採用 |
| 類似条件平均との差 | 駅・面積・築年中心 | 小 | 既存価格推移JSON | モデル理由ではなく市場比較 | 補助情報 |
| グローバル特徴量重要度 | 個別入力ではない | なし | 既存メタデータ | 個別理由と誤認しやすい | 詳細欄のみ継続 |

ONNX Runtime Webは現行モデルの推論結果を返すが、個別TreeSHAPを直接返さない。モデル内部を
ブラウザで別途解析する実装は、初回JavaScript容量、保守対象、Pythonとの整合確認を増やすため、
MVPでは採用しない。

## 採用方式

学習行からユーザー編集可能な特徴量の代表値をモデルメタデータへ出力する。

- 面積、築年数、駅徒歩: 中央値
- 間取り、建物構造: 最頻値
- 予測年: 理由計算では変更しない
- 都道府県、市区町村、最寄駅: 選択地点を維持する
- 地価、用途地域、駅規模: 選択地点に従うため変更しない

現在入力の予測を基準とし、対象特徴量を1つだけ代表値へ置き換えて再推論する。

```text
差分 = 現在条件の予測価格 - 代表値へ置換した予測価格
```

- 正の差分: 「価格を押し上げるモデル上の要因」
- 負の差分: 「価格を押し下げるモデル上の要因」
- 差分が小さいものは表示しない
- 絶対差分が大きい順に各3件まで表示する

同じ入力から作る反実仮想比較であり、「面積を増やせば必ずこの金額だけ上がる」といった因果効果は
示さない。相関する特徴量や学習データの偏りを含む可能性を常に併記する。

## 将来予測の扱い

学習最終年より後の表示価格は、ONNXモデルの学習最終年価格へ駅別・地域別トレンドを適用している。
入力条件の理由は学習最終年のモデル差分として表示し、将来補正は別項目で「駅別傾向」または
「地域傾向」として表示する。両者を一つの寄与額へ混ぜない。

## 成果物契約

モデルメタデータへ任意項目 `inputBaselines` を追加する。旧メタデータでは理由表示を行わない。

```json
{
  "inputBaselines": {
    "area": 65.0,
    "age": 24.0,
    "stationDistance": 9.0,
    "roomLayout": "3LDK",
    "buildingType": "ＲＣ"
  }
}
```

追加JSONは作らず、数十〜数百バイトのメタデータ増加に留める。モデルセッションとカテゴリ辞書は
現在の予測と共用し、追加ネットワークリクエストは発生させない。

## 性能予算と検証

- 追加推論: 最大5回
- 追加転送量: 1モデル当たり1KB未満
- 再予測全体: デスクトップ200ms以内を目安
- 入力変更中は既存の250msデバウンス後に一度だけ計算する
- Pythonとブラウザで同一入力・同一代表値の差分方向と金額を照合する
- E2Eで押し上げ・押し下げ・理由なし・旧メタデータを確認する

初回実装では実測値を保存し、上限を超える場合は数値特徴量3項目へ絞る。

## 初回実測

2026年8月5日に全12モデルへ代表値を追加した結果、メタデータ合計は104,315バイトから
106,069バイトとなり、増加は1,754バイト、1モデル平均約146バイトだった。追加モデル・追加
リクエストはない。Chromium E2Eでは東京都の実モデルで理由計算が200ms未満であることを確認した。

間取りはUIが半角、国交省データとカテゴリ辞書が全角であるため、推論前に英数字を全角へ正規化する。
これにより間取りが未知カテゴリへ落ちる不整合も解消する。
